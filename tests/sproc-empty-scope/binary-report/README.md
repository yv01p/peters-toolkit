# binary-report/ — provenance (answer key — never sent to a rep)

`BINONLY1-SPROC-XRAY.md` is the migration-plan-side input fixture for the
**binary-gate** reps (`planning-binary` cell). It is a **real x-ray report**,
generated by running the shipped `sproc-xray` (v0.5.0) over the finding-A
binary corpus `tests/sproc-xray-binary/binonly1/` (a SQL Server `.mdf` with no
text SQL export), so it carries the validator markers AND the binary signal by
construction.

- **Source corpus:** `tests/sproc-xray-binary/binonly1/` (`sample_db.mdf` +
  README answer key; the README is excluded from the rep-facing copy).
- **Generated by:** Task 1 Step 2, a fresh blind x-ray rep (sonnet) over a
  README-excluded copy of the corpus.
- **Shape:** empty `### Extraction Metrics` table, **binary signal present in
  both anchors** — the Context-Intake row (`Binary DB files (unparsed) … Yes |
  1`) and the `## Confidence & Coverage Declaration` binary line — plus the
  three name-only routines (`sp_calculate_driver_payout`, `fn_apply_late_fee`,
  `trg_audit_vehicle_status`) surfaced but excluded from every count (finding
  A's shipped v0.5.0 behavior). Full validator markers present.
- **Normalization:** the rep's proof-block source paths (generated under a
  neutral sandbox dir) were rewritten to the canonical corpus name `binonly1`;
  the analysis (counts, findings, binary verdict, proof-block outputs) is
  untouched.

The migration-plan binary-gate rep must accept this at intake (markers
present, and input #2 = the `binonly1` corpus exists) and, post-fix, DEFER
("logic likely resides in an unparsed binary; export DDL and re-run") rather
than emit an empty backlog.
